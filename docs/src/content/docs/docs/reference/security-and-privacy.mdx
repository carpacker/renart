---
title: Security and privacy
description: Renart's local trust boundary, network exposure, telemetry, and safe workspace practices.
---

Renart runs locally against files and connections you control. It does not
require an account or a hosted Renart control plane, and the application does
not send usage telemetry.

## Keep the server local

The web server listens on `127.0.0.1` by default. Keep that default unless you
have a trusted access layer: Renart can edit workspace files and execute
pipeline and notebook code, and it does not provide remote-user
authentication.

Binding to a non-loopback address requires `--unsafe-allow-remote` and prints a
warning. The flag is an acknowledgement of the risk, not an authentication
feature.

## Treat workspaces as executable input

Opening and browsing files is distinct from running them, but materializing a
pipeline or running a notebook can execute SQL, Python, and connector logic
from the workspace. Review an unfamiliar repository and its dependencies
before running it. Use warehouse credentials limited to the environments and
operations the project needs.

Renart stores local operational state in the workspace's `.renart` directory.
Keep pipeline source in Git, but do not commit state databases, credentials, or
generated runtime files.

## Website analytics

The Renart application has no analytics integration. The documentation site's
static build also contains no analytics by default; a site operator can
explicitly inject a self-hosted analytics script while deploying the website.
That website setting does not affect a locally running Renart instance.

## Report a vulnerability

Do not publish suspected vulnerabilities in an issue. Use
[GitHub's private vulnerability reporting](https://github.com/renart-data/renart/security/advisories/new)
with the affected version, impact, and reproduction steps.
