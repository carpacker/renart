Notebooks are where analysis starts before it deserves a place in the
pipeline. Each notebook is a folder of SQL and Python cells that runs in its
own local DuckDB session, reading the tables your pipeline has materialized —
so you can explore freely without touching pipeline state.

## Cells

Each cell is a named SQL query or Python transformation. Run one cell, run from
a cell downward, or **Run all**. Results render inline as a table, with view
toggles for bar, line, area, and pie charts.

Python cells use the same `materialize()` contract as Python pipeline assets.
They can read an upstream notebook cell by its visible name through the built-in
SDK:

```python
from renart import query


def materialize():
    orders = query("select * from daily_orders")
    return orders
```

Use **Dependencies** to manage third-party packages. Python cells run manually;
editing one does not trigger notebook auto-recompute. The built-in runtime
already includes pandas and PyArrow; adding any other package creates the
notebook's Python project on demand.

SDK queries run against the notebook's live local session. Renart rewrites the
visible upstream names inside the runner, so Python receives query results but
never a database path or connection credentials.

## Charts with @viz

Pin a cell's default visualization with a `@viz` comment on its first line:

```sql
-- @viz(line, x: order_date, y: revenue)
SELECT order_date, ROUND(revenue, 2) AS revenue
FROM mart.daily_revenue
ORDER BY order_date
```

The arguments are `key: value` pairs — the chart kind first, then the
columns to map.

## Promote a cell to the pipeline

When a query earns a permanent place, open the cell's actions menu and
choose **Promote to pipeline**. The cell becomes a real SQL asset in the
pipeline you pick — same repo, same review flow as everything else.

## Files like everything else

A notebook lives in your repository as a folder of `.sql` cell files, so
notebooks are versioned, diffable, and reviewable exactly like pipeline
code.
