# Building your own Renart

A primer for developing a divergent fork. Assumes you've read `WINDOWS-DEV.md`
for setup and the codebase map.

Your stated direction: an AI/agent layer, IDE features, and guaranteed
connectivity to specific platforms — modifying upstream code freely where
convenient.

---

## 0. What you actually forked

Renart is thinner than it looks. **Bruin does the data work.** Renart is the IDE
around it.

`github.com/bruin-data/bruin` (pinned in `go.mod`, currently ~v0.11.691) owns:
connection struct schemas and their tags, the asset-type↔connection mapping,
every per-warehouse operator and materializer, the pipeline/asset file format,
and most SQL dependency semantics. Renart owns the HTTP/service layer, the
secret indirection, staleness/fingerprinting, the scheduler around River, the
reflection-driven connection UI, and a direct in-process executor registry that
re-implements Bruin's CLI dispatch without shelling out to a binary.

This split determines what's cheap and what's expensive for you. Anything that
requires a **new Bruin type** means patching or forking Bruin too. Anything that
sits in Renart's own layer is yours to change freely.

### Upstream is moving fast

- **164 commits in the last 30 days. 331 in 90.**
- Hottest directory by a wide margin: `internal/web/service` (768 file-touches
  across the last 200 commits). Then `web/components/app`, `web/tests/e2e`,
  `internal/web/scheduler`.
- Most-churned individual files: `architecture/backend.md`, `web/lib/generated/api-types.ts`,
  `web/components/app/build-page.tsx`, `cmd/web.go`, `cmd/server.go`,
  `internal/web/service/direct_run.go`, `internal/web/service/execution.go`,
  `internal/web/model/dto.go`.

You chose to modify freely, which is a legitimate call — it's your fork and
velocity matters more than merge hygiene early on. But be aware of the bill:
those churn-heavy files are *exactly* the files a feature touches. `cmd/web.go`
for route wiring, `dto.go` for types, `build-page.tsx` for UI. Every one is a
recurring conflict.

The mitigation isn't discipline, it's **placement**. Put your logic in new files
and touch the hot files in as few lines as possible. A one-line route
registration in `cmd/web.go` conflicts trivially; a 200-line handler inlined
there conflicts every week.

### Decide your merge posture now

Pick one and write it down, because the cost compounds:

- **Rebase your work onto upstream weekly.** Conflicts stay small and you always
  know which change broke what. Costs an hour a week.
- **Merge upstream in batches monthly.** Fewer interruptions, much bigger
  conflict surface each time.
- **Snapshot and stop tracking.** Pin to a known-good upstream commit and only
  pull deliberately, for specific fixes. Cheapest day-to-day, and you inherit
  none of their improvements.

At 164 commits/month, drifting for six months without a decision means an
effectively unmergeable fork. That's fine if it's chosen; it's expensive if it's
an accident.

## 1. The seams — where your code should live

Some of Renart's structure is genuinely load-bearing for a fork, because it lets
you add without editing.

### Reflection-driven connection UI — the best seam in the codebase

`BuildWorkspaceConfigConnectionTypes()` in `internal/web/service/config.go`
reflects over Bruin's `config.Connections` struct and derives the entire
connection form: field names from `mapstructure` tags, required-ness from
`yaml:omitempty`, defaults from `jsonschema`, and sensitivity from Bruin's
`sensitive:"true"` / `sensitive_file:"true"` tags.

`web/components/workspace-connection-form-fields.tsx` iterates that metadata
generically. **There is no hardcoded per-platform field list anywhere, frontend
or backend.**

Consequence: adding a field to a Bruin connection struct produces a correctly
masked, write-only form field in the UI with zero Renart changes. Don't fight
this by special-casing platforms in the frontend — you'd be reintroducing the
name heuristics the design deliberately removed.

### Generated files — never resolve these by hand

- `web/lib/generated/api-types.ts` — generated by `web/scripts/generate-api-types.mjs`,
  which parses Go structs out of `internal/web/model/dto.go` and friends.
- `web/src/routeTree.gen.ts` — generated by the TanStack Router Vite plugin.

Both are in the top-churn list. On a conflict, **take either side and
regenerate**:

```powershell
Push-Location web; corepack pnpm generate:api-types; Pop-Location
```

Add a new DTO's name to the `sources[].types` array in
`generate-api-types.mjs` or the frontend won't see it.

### Transaction precedent

`internal/web/service/asset_transactions.go` is the existing pattern for
semantic, typed mutations against a single asset (operations like
`dependency.manual.add`, POSTed to `/api/assets/{assetID}/transactions`, per-file
lock, reconcile, atomic write). Whenever you're tempted to add a raw
"write these bytes" endpoint, model it as a transaction instead. It's also the
thing upstream's agent plan explicitly builds on.

## 2. Track: connectivity (start here — highest certainty, lowest cost)

"Ensure certain connectivities" splits into two very different jobs. Figure out
which one you're in before writing code.

### If Bruin already supports the platform

Mostly registry wiring, and the credential UI + API types come free:

1. `internal/web/service/direct_executor_registry.go` — register the main
   operator in `buildDirectMainExecutors`, plus seed/sensor variants via
   `assignSeedExecutor` / `assignSensorExecutor`.
2. `internal/web/service/direct_run.go` — add it to `directRunAssetTypes` so
   `isDirectRunAssetTypeSupported` stops rejecting it.
3. `internal/web/service/direct_check_registry.go` — if it needs check operators.
4. `internal/web/service/direct_materializer.go` — if it needs hook-aware or
   ordered-statement semantics. Skip this and
   `POST /api/pipelines/{id}/assets/render` marks its stages `unsupported`.
5. Extend the `direct_*_parity_test.go` suites.

Already wired: DuckDB, MotherDuck, Postgres, Redshift, BigQuery, Athena,
Databricks, Doris, Fabric, MySQL, Snowflake, MSSQL, Synapse, ClickHouse,
StarRocks, Trino, Dremio/Sail, Vertica, Oracle (query-only), plus Python,
Ingestr, and an S3 key sensor.

**Fail-closed, not fallback.** `architecture/backend.md` describes a "CLI
fallback" to the `bruin` binary. That is stale — in current code,
`shouldFallbackToCLIRunAsset` returns an error, and there's no
`exec.Command("bruin", ...)` in the execution path. The only real CLI executor
is `cliCompatExecutor` in `direct_executor_test.go`, used to assert parity. So
an unregistered asset type is a hard error, not a slow path. Good news for
predictability; means step 2 above is not optional.

### If Bruin does not support the platform

Do **not** invent a new typed connection struct in Renart. The reflection
contract assumes one struct in `config.Connections`, and duplicating it outside
breaks the "one struct, one form, one type" guarantee. Your options, cheapest
first:

- **HTTP API assets** (`architecture/http-api-assets.md`) — no connection type at
  all. Auth, pagination, and OpenAPI live inline in the asset YAML; Renart's own
  extractor streams to JSONL and Sling loads it into the warehouse. This is the
  intended escape hatch for arbitrary sources, and it touches no Bruin code.
- **Load assets via the Sling bridge** — if Sling has a connector. The bridge
  already does hand-written per-platform shape translation (Trino query props,
  ClickHouse DB path + TLS, DuckLake catalog strings, StarRocks payloads,
  Postgres `sslmode` rewriting). Extending it is normal fork work.
- **Patch Bruin.** Fork `bruin-data/bruin`, add the connection struct and
  operator, and point `go.mod` at your fork with a `replace` directive. Once the
  struct exists with correct tags, Renart's reflection and registry work is
  comparatively small. This is the only path to a true first-class warehouse
  type — and it means you now maintain two forks.

## 3. Track: IDE features

The full path through the stack, in order:

1. `internal/web/model/dto.go` — the DTO
2. `internal/web/service/<domain>.go` (+ `_test.go`) — the logic. **Put this in a
   new file**, not appended to an existing one; `service/` is the hottest
   directory in the repo.
3. `internal/web/httpapi/<domain>.go` — handler. Decode → delegate → encode, no
   logic.
4. `cmd/web.go` — route wiring. Keep it to one line.
5. `web/scripts/generate-api-types.mjs` — register new types, then regenerate.
6. `web/lib/api-<domain>.ts` — client function.
7. `web/components/app/` — the component, wired into `build-page.tsx`.
8. `web/lib/atoms/` — Jotai state if shared.

A new page is a file under `web/src/routes/_shell/` plus a nav entry in
`web/components/app/app-data.ts`.

Note `web/components/redesign/` exists alongside `web/components/app/` and has
its own `build-page.tsx` — upstream is mid-redesign. Check which one is live
before investing in a UI change, or you'll build on a surface that's being
replaced.

## 4. Track: the AI/agent layer

Read `plans/agentic-notebooks.md` before writing a line. It's ~1,200 lines,
dated 2026-07-14, and labeled **"research proposal only — not implemented."**
That label is accurate: I checked.

### There is nothing to build on, and nothing in your way

The codebase has **zero** LLM/agent machinery today. No client, no completion
endpoint, no prompt handling. Every `agent` hit in the source is a `User-Agent`
header. `cmd/completion_outbox.go` is a *run-completion* event outbox (durable
`bus.RunCompleted` replay after crash) — not shell completion, not LLM
completion. The `aiChat` UI mockup that `plans/agentic-notebooks.md` §3.4 cites
was static markup and has since been deleted upstream (commit `aaef798`); that
citation is stale.

So this is a blank slate. Nothing to rip out, and no upstream code to conflict
with — for now. Note that AGENTS.md names AI agents as upstream's own long-term
direction, so this is the area where your fork is most likely to eventually
collide with theirs.

### What the plan actually recommends

Worth taking seriously — it's a well-reasoned document, and following its shape
keeps a future reconciliation possible.

- **Notebook-scoped staged agent**, not a chat sidebar and not a background
  worker. The agent reads bounded context through typed tools, proposes a
  multi-cell change set that never touches real files, validates SQL in an
  isolated scratch DuckDB session, and the user explicitly applies. The applied
  result is an ordinary unstaged git diff. The agent never commits.
- **One provider-neutral `NotebookAgentService`**, two clients: an MCP/external-agent
  bridge first (cheaper, model supplied externally), then a native staged panel.
- **A closed tool catalog** — `get_notebook_outline`, `get_cell`,
  `diagnose_draft`, `run_scratch_sql`, `stage_cell_create/update`,
  `preview_change_set`. Deliberately **no** `apply_change_set`, no shell, no
  generic file read/write, no git, no web search.
- **Autonomous background analysis is explicitly rejected** — nondeterminism
  against reactive reproducibility, plus persistent prompt-injection risk.

Phasing: (0) fixed task-corpus spike, (1) agent-safe notebook foundation —
durable markdown IDs, notebook-wide snapshot revisions, overlay/change-set
machinery, scratch sessions, all backend-only with no model involved, (2)
external-agent MCP preview, (3) native panel, (4) broaden.

### Where it plugs in

- **Host:** `internal/web/notebook/` — loader, DAG, runner, session, promote.
  Already has the ingredients: stable frontmatter cell IDs (filenames are
  cosmetic), a per-notebook private DuckDB session serialized by mutex, Python
  cells brokered so credentials never reach the Python process (data returns via
  Parquet), and plain-file git-native storage.
- **Service layer:** beside `NotebookService` in `internal/web/service/`, calling
  the same loader and runner rather than reparsing folders.
- **Tool backends you get for free:** `internal/sqlintelligence/` (parser,
  lineage, used-tables, schema, output-drift, validator) and `internal/sqllsp/`
  back a `diagnose_draft` tool directly.
- **Brokering model:** `internal/web/pybroker` — loopback HTTP, bearer token,
  read-only enforcement, credentials never leaving Go. Built for the Python SDK,
  and structurally almost exactly what an agent tool-call boundary needs. Copy
  this pattern.

### Two hazards the plan itself flags

**The same-origin guard doesn't stop a local process.**
`SameOriginGuardWithToken` in `internal/web/httpapi/middleware.go` deliberately
lets non-browser clients with no `Origin` header through, for CLI compatibility.
So an external MCP-bridged agent can bypass your carefully bounded tool surface
by just calling the ordinary mutating APIs. If you build the external bridge
without a short-lived, scope-pinned capability token, the "bounded tools" story
is cosmetic rather than enforced. Fix this before, not after.

**Notebook-wide atomic apply doesn't exist.** Today's endpoints in
`httpapi/notebooks.go` mutate one thing at a time. There's a per-cell SHA-256
`content_revision` / `base_revision` check that 409s on stale writes — but it's
cell-level. Looping an agent over those endpoints is the plan's explicitly
"rejected shortcut": partial failure corrupts notebook state. The
`NotebookFileTransaction` design (journal, same-filesystem temp files, rollback)
is a real subsystem you'd need to build first.

## 5. Constraints that are architecture, not taste

You said you'd modify freely. These four are still worth keeping, because
breaking them costs you correctness rather than upstream goodwill:

- **SSE only, no polling.** Workspace sync flows through one `/api/events`
  connection with server-side reconciliation. Agent activity needs its *own*
  stream with monotonic sequence IDs — don't multiplex onto the workspace hub,
  which drops slow-client events by design.
- **All filesystem writes go through the Go server. No Node runtime in
  production.** Rules out any agent harness assuming a Node or Python
  orchestrator. Your tool runtime is Go, in the same binary.
- **Inspect is read-only, single `SELECT`.** Materialization is the only
  side-effecting path. An agent's `run_scratch_sql` must preserve this exactly.
- **Secrets are typed references, never values.** `.renart/secrets.yml` stores
  `provider:key#field` coordinates only. Sensitivity comes from reflected Go
  struct tags, resolution is purpose-scoped (`connection_validation`, `inspect`,
  `query`, …), and leases zero their buffers on close. Never add a frontend
  heuristic for which fields are sensitive, and never let a resolved value reach
  logs, argv, SSE, or `state.db`.

Two more that are just facts about the platform:

- **cgo is mandatory on Windows.** `internal/web/adbcutil` uses `import "C"` and
  the server imports it transitively. Only `renart-gui.exe` builds without it.
- **Python is brokered, not sandboxed.** Credential brokering keeps secrets out
  of the Python process; it does *not* stop generated Python from touching the
  host filesystem or network. Never auto-execute agent-generated Python.

## 6. Merge workflow

```powershell
git fetch upstream
git log --oneline main..upstream/main          # what landed
git checkout main
git merge --ff-only upstream/main
git checkout carson/my-feature
git rebase main
```

When conflicts hit:

- **Generated files** (`api-types.ts`, `routeTree.gen.ts`) — take either side,
  regenerate, move on.
- **`cmd/web.go` route lists** — almost always "keep both."
- **`dto.go`** — usually "keep both," but check whether upstream renamed a field
  you depend on.
- **`internal/web/service/*`** — the expensive ones. If you're conflicting here
  every merge, that logic wants to move into a file of its own.

Then verify, because a clean merge is not a working merge:

```powershell
.\make.ps1 check
```

Keep a branch per feature rather than one long-lived mega-branch. When a rebase
goes badly you want to lose one feature's worth of work, not all of it.

## 7. Concrete first moves

1. **Read `plans/agentic-notebooks.md` end to end.** It's the single highest-value
   document in the repo for your direction, and it will change what you build.
2. **Make one trivial full-stack change** to prove the loop: add a field to a DTO,
   regenerate types, surface it in a component. You'll learn the codegen step by
   doing it once, cheaply.
3. **Pick your one connectivity target** and determine which side of the Bruin
   line it falls on. If it's Bruin-supported, the registry wiring is a
   satisfying first real change. If not, prototype it as an HTTP API asset before
   considering a Bruin fork.
4. **Decide your merge posture** (§0) and put a recurring reminder on it.
5. **Before any agent work**, close the capability-token gap in
   `middleware.go`. Everything else in the agent plan assumes a bounded tool
   surface that doesn't currently exist.

### Things I'd verify rather than trust

`architecture/` is the most-churned documentation in the repo and it's already
stale in at least one load-bearing place — the CLI-fallback description in
`backend.md` doesn't match the code. Treat those docs as a strong map, not as
truth. When a doc and the code disagree, the code is right.
